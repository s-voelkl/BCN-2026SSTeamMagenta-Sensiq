\section{Evaluation}\label{sec:evaluation}

\subsection{Testability}\label{sec:testability}
The cloud system's testability is ensured through rigorous automated checks for
both infrastructure and application logic. Local \texttt{yarn} scripts automate
test execution and coverage reporting.

\subsubsection{AWS Infrastructure}
The AWS cloud infrastructure configuration is automatically validated using
built-in AWS Cloud Development Kit (CDK) assertions, leveraging the
\texttt{Template} and \texttt{Match} constructs. This ensures that the generated
resources and policies match the intended architectural design prior to deployment.

\subsubsection{AWS Lambda Handlers}
AWS Lambda functions are thoroughly unit-tested using Python's \texttt{unittest}
or \texttt{pytest} frameworks, employing exhaustive mocking to isolate execution
behavior. To evaluate Lambda handlers independently of the API Gateway, a locally
defined \texttt{TestEvent} JSON payload is utilized to replicate realistic
incoming requests during testing. Additionally, for runtime observance and
debugging in the deployed environment, Lambda function executions and errors
are continually logged to dedicated AWS CloudWatch log groups.

\subsubsection{Sensor Node Firmware}
Firmware unit testing utilizes the AUnit framework~\cite{aunit_testing_arduino}
to cover modules like sensor readings, data aggregation, configurations, and Wi-Fi. Exhaustive
MQTT mocking was omitted due to real-world deviations. Instead, the node
subscribes to an MQTT test topic during operation to directly verify connection
health and publish functionality.

\subsubsection{AWS Service Costs}\label{sec:aws-costs}
The figures in \cref{tab:aws-costs} reflect a monthly cost estimate
based on an ESP-32 publishing one message every five seconds (roughly
518\,000 messages per month). AWS IoT Core is the absolute dominant cost driver.
Because each payload is evaluated against two IoT Core rules, AWS bills
three units per publish, resulting in 1\,554\,000 billed message units.
This accounts for over 75\% of the total monthly cost (\$1.62).

Other minor expenses stem from Kinesis Data Firehose applying a 5\,KB minimum
billing unit---inflating the logical data volume to 2.59\,GB (\$0.08 per month
with no free tier)---and Athena scanning costs for an estimated 660 history queries
per month. Storage, routing, and alert notification costs remain trivial.

The table contrasts the \emph{Free Tier} expenditure of a new AWS account
against the ongoing \emph{Post Free Tier} cost once initial allowances expire.
Overall, the architecture operates highly cost-efficiently, totalling approximately
\$1.88 and \$2.13 per node per month, respectively.

\subsection{Discussion}\label{sec:discussion}

Currently, the API Gateway Access Key is stored stored as an environment variable in the React frontend and
sent in the header of API requests. This approach is not ideal for security, as it exposes
the key in the client-side code and can lead to unauthorized access if the key is compromised.
In future iterations, we plan to leverage AWS Cognito for user authentication and authorization.

Operating costs for AWS services could be further reduced by decreasing the publishing frequency from every 5 seconds
to a more conservative interval, such as every 30 seconds. This would substantially lower recurring expenses; however,
it would compromise real-time monitoring objectives, as critical events might not be detected promptly. Reduced publishing
frequency is therefore only viable in scenarios with relaxed real-time requirements.

If the publishing frequency is decreased, implementing a Deep Sleep mode for the ESP32
microcontroller would be a logical next step to significantly extend battery life.
However, this is only viable with longer measurement intervals (e.g., every 30 seconds or more).
During high-frequency measurements, Deep Sleep could disrupt MQTT connectivity and the sensor
reading lifecycle, as the ESP32 is entirely unreachable while in this mode.

Configuring recipients for warning notifications requires manual intervention
via the AWS Dashboard. Future iterations should integrate this functionality directly into
the React frontend, though this enhancement would require an additional AWS Lambda function
designed to update an Amazon DynamoDB table, allowing end-users to seamlessly add
or remove notification recipients for specific devices.

Warning thresholds should ideally be configurable on a per-device basis to accommodate
varying environmental conditions and requirements.
Though, at this stage, thresholds are hardcoded in the Lambda function for simplicity.
Using a DynamoDB table to store device-specific thresholds would allow for dynamic updates without code changes.

As demonstrated in~\cite{mumtaz2021internet}, integrating machine learning models
into Indoor Air Quality (IAQ) monitoring systems can significantly enhance their
capabilities by enabling predictive analytics or advanced anomaly detection.
A promising enhancement for this architecture involves deploying an outlier detection
model on AWS. This could be achieved by utilizing an AWS Lambda function to process the
live data stream in real time, identifying anomalies based on an Amazon SageMaker model
pre-trained on historical data. This anomaly-detection could complement the existing
threshold-based alerting mechanism, providing an additional layer of safety and data insight.
