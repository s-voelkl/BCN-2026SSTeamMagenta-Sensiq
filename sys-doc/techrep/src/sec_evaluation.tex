\section{Evaluation}\label{sec:evaluation}

A comprehensive evaluation of the testability, cost estimation, and architectural trade-offs
is presented in the following subsections.

\subsection{Testability}\label{sec:testability}
The cloud system's testability is ensured through rigorous automated checks for
both infrastructure and application logic. Local \texttt{yarn} scripts automate
test execution and coverage reporting.

\subsubsection{AWS Infrastructure}
The AWS cloud infrastructure configuration is automatically validated using
built-in AWS Cloud Development Kit (CDK) assertions, leveraging the
\texttt{Template} and \texttt{Match} constructs. This ensures that the generated
resources and policies match the intended architectural design prior to deployment.

\subsubsection{AWS Lambda Handlers}
AWS Lambda functions are thoroughly unit-tested using Python's \texttt{unittest}
or \texttt{pytest} frameworks, employing exhaustive mocking to isolate execution
behavior. To evaluate Lambda handlers independently of the API Gateway, a locally
defined \texttt{TestEvent} JSON payload is utilized to replicate realistic
incoming requests during testing. Additionally, for runtime observance and
debugging in the deployed environment, Lambda function executions and errors
are continually logged to dedicated AWS CloudWatch log groups.

\subsubsection{Frontend}
The React frontend is tested with Vitest~\cite{vitest}, covering the helper functions
and verifying that sample data is rendered correctly to the document.

\subsubsection{Sensor Node Firmware}
Firmware unit testing utilizes the AUnit framework~\cite{aunit_testing_arduino} to cover
modules like sensor readings, data aggregation, configurations, and Wi-Fi. Exhaustive
MQTT mocking was omitted due to real-world deviations. Instead, the node
subscribes to an MQTT test topic during operation to directly verify connection
health and publish functionality.

\subsubsection{AWS Service Costs}
The figures in \cref{tab:aws-costs} reflect a monthly cost estimate
based on an ESP-32 publishing one message every five seconds (roughly
518\,000 messages per month). AWS IoT Core is the absolute dominant cost driver.
Because each payload is evaluated against two IoT Core rules, AWS bills
three units per publish, resulting in 1\,554\,000 billed message units.
This accounts for over 75\% of the total monthly cost (1.41\,\texteuro).

Other minor expenses stem from Kinesis Data Firehose applying a 5\,KB minimum
billing unit---inflating the logical data volume to 2.59\,GB (0.07\,\texteuro~per month
with no free tier)---and Athena scanning costs for an estimated 660 history queries
per month. Storage, routing, and alert notification costs remain trivial.

The table contrasts the \emph{Free Tier} expenditure of a new AWS account
against the ongoing \emph{Post Free Tier} cost once initial allowances expire.
Overall, the architecture operates highly cost-efficiently, totalling approximately
1.64\,\texteuro~and 1.87\,\texteuro~per node per month, respectively.

\subsection{Discussion}\label{sec:discussion}

The evaluation reveals several architectural trade-offs regarding cost, latency, scalability, and security:

First, storing the API Gateway Access Key in the React frontend simplifies prototyping but
presents a client-side security vulnerability. Production deployments necessitate a robust
identity layer (e.g., AWS Cognito) to securely broker API transactions.

Second, the 5-second publishing interval ensures instantaneous anomaly alerting but drives up AWS
IoT costs and edge power consumption (\cref{tab:aws-costs}). While reducing this frequency
(e.g., to 30 seconds) would lower costs and allow the ESP32 to utilize Deep Sleep,
this power-saving mode severs network availability and requires costly TLS handshakes upon waking.
Consequently, strict real-time latency is structurally incompatible with extreme low-power sleep modes.

Third, hardcoding warning thresholds and notification recipients within Lambda functions minimizes
complexity and prevents database read latencies during live execution. However, this static
configuration lacks the flexibility needed for scalable, adjustable, multi-tenant laboratory deployments.

Finally, relying on absolute static thresholds fails to detect degrading air quality trends before
critical hazards are breached~\cite{mumtaz2021internet}.
Preemptive anomaly detection requires contextual pattern evaluation beyond rigid limits,
such as machine learning analysis over historical data. Implementing machine learning
for detecting anomalies (outliers) in live data instead of relying solely on thresholds
would significantly enhance the outlier detection capabilities of the system for laboratory environments.
