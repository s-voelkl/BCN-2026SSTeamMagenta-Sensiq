\section{Evaluation}\label{sec:evaluation}

\subsection{Testability}\label{sec:testability}
The cloud system's testability is ensured through rigorous automated checks for
both infrastructure and application logic. Local \texttt{yarn} scripts automate
test execution and coverage reporting.

\subsubsection{AWS Infrastructure}
The AWS cloud infrastructure configuration is automatically validated using
built-in AWS Cloud Development Kit (CDK) assertions, leveraging the
\texttt{Template} and \texttt{Match} constructs. This ensures that the generated
resources and policies match the intended architectural design prior to deployment.

\subsubsection{AWS Lambda Handlers}
AWS Lambda functions are thoroughly unit-tested using Python's \texttt{unittest}
or \texttt{pytest} frameworks, employing exhaustive mocking to isolate execution
behavior. To evaluate Lambda handlers independently of the API Gateway, a locally
defined \texttt{TestEvent} JSON payload is utilized to replicate realistic
incoming requests during testing. Additionally, for runtime observance and
debugging in the deployed environment, Lambda function executions and errors
are continually logged to dedicated AWS CloudWatch log groups.

\subsubsection{Sensor Node Firmware}
Firmware unit testing utilizes the AUnit framework~\cite{aunit_testing_arduino}
to cover modules like sensor readings, data aggregation, configurations, and Wi-Fi. Exhaustive
MQTT mocking was omitted due to real-world deviations. Instead, the node
subscribes to an MQTT test topic during operation to directly verify connection
health and publish functionality.

\subsubsection{AWS Service Costs}\label{sec:aws-costs}
The figures in \cref{tab:aws-costs} reflect a monthly cost estimate
based on the following usage assumptions: the ESP-32 publishes one message
every five seconds, yielding roughly 518\,000 messages per month. Each
message is evaluated against two IoT Core rules, and AWS bills the inbound
message plus one unit per rule, resulting in 1\,554\,000 billed message
units at \$1.00 per million, making IoT Core the dominant cost driver at
\$1.62 per month. Both rules trigger on every message: one forwards the
payload to Kinesis Data Firehose for long-term storage, the other invokes
the \texttt{handleTransformValidate} Lambda function. Firehose applies a
5\,KB minimum billing unit per record, inflating the effective ingested
volume from \textasciitilde197\,MB to \textasciitilde2.59\,GB and
resulting in a flat \$0.08 per month regardless of account age, as
Firehose carries no free tier. The React frontend is served from a plain
S3 bucket, incurring no meaningful storage cost. History queries are
assumed to occur ten times per day across all users, totalling around 660
monthly Athena queries; the scanned data volume is estimated at 50\,MB per
query, reflecting a mid-range time window against the Parquet-partitioned
S3 bucket (partitioned by year, month, and day), with partition pruning
keeping scan sizes stable as data accumulates. The Glue Data Catalog is
maintained via a handwritten schema definition, incurring no crawler cost.
SNS alerts are treated as negligible, firing approximately three times per
week.

The table is split into two cost columns: \emph{Free Tier} reflects the
first twelve months of a new AWS account, during which Lambda, API
Gateway, and SNS remain within their monthly free allowances.
\emph{Post Free Tier} represents the ongoing monthly cost once those
allowances expire. Both estimates are recurring on a monthly basis and
total approximately \$1.88 and \$2.13 respectively, with IoT Core alone
accounting for over 75\% of the total cost in both scenarios.
