\section{AWS Services}\label{sec:aws_services}
% TODO: remove section information
Detailed description of the cloud-side processing pipeline. Two
functional routes are exposed by the backend: a low-latency live
route and a long-term history route. Each is described in its own
subsection together with the AWS services it relies on.

\subsection{Live Route}\label{sec:live_route}
The live route provides a low-latency data delivery mechanism, exposing a
\texttt{POST /live} endpoint via API Gateway. It returns the most recent
sensor reading as a structured JSON payload. The pipeline spans from hardware
ingestion through serverless transformation to a managed NoSQL store.

\subsubsection{Data Ingestion and Transformation}
Sensor readings are assembled on the ESP-32 microcontroller and published
via MQTT to AWS IoT Core~\cite{awsIotCore}. An IoT topic rule
forwards each incoming message to the
\texttt{handleTransformValidate} Lambda function. This function is
responsible for validating and transforming the payload to the internal data format,
and classifies outlier readings against predefined thresholds, as described in
\cref{sec:sns_notifications}. Regardless of classification,
the validated record is written to a DynamoDB
table~\cite{aws-dynamodb} (\texttt{LiveDataDB}) via a \texttt{PutItem}
operation, which always reflects the latest device state.

\subsubsection{Live Data Retrieval}
Incoming \texttt{POST /live} requests are routed through the API Gateway to the
\texttt{handleLiveData} Lambda function. This function performs a read
against \texttt{LiveDataDB} and returns the latest sensor record as a
JSON response. Because the data is served directly from DynamoDB with
single-digit millisecond read latency, the live route consistently
responds well within the 29-second API Gateway timeout, typically in
under one second. The handler returns an error response when the entry in
\texttt{LiveDataDB} is older than 60 seconds.

\subsection{History Route}\label{sec:history_route}
The history route provides a long-term data retrieval mechanism, exposing a
\texttt{POST /history} endpoint via API Gateway. It accepts query parameters
such as time ranges, limits, aggregation precision and a device ID, and returns
precision-adjusted aggregated historical sensor data as a structured JSON payload.
The pipeline bridges data ingestion from AWS IoT Core to a highly optimized query backend.

\subsubsection{Data Ingestion and Storage}
Incoming JSON messages from AWS IoT Core are captured by an IoT rule and
forwarded to Amazon Kinesis Data Firehose~\cite{aws-firehose}. To mitigate
the small-files problem, Firehose buffers the data for up to 15 minutes or
until a size of 128\,MB is reached before converting it to Apache Parquet
format. The Parquet files are written to a S3 Standard data
bucket~\cite{aws-s3-storage-classes},
partitioned by year, month, and day to ensure efficient storage and rapid
retrieval. S3 lifecycle management policies~\cite{aws-s3-lifecycle-management}
are configured to retain the data securely for an extended period, while an
AWS Glue Data Catalog maintains the structural metadata of the
\texttt{sensor\_data} table. IAM policies tightly control access to the Glue
catalog and underlying S3 buckets~\cite{aws-athena-iam-policies}.

\subsubsection{Query Execution and Processing}
A dedicated AWS Lambda function coordinates the fulfillment of history
requests. It parses the incoming query parameters, validates them, and
constructs an Athena query using query execution
parameters~\cite{aws-athena-execution-parameters} to defend against SQL attacks.
Athena utilizes Glue's partition projection
mapping~\cite{aws-athena-partition-projection} to prune directories rapidly
without needing to load external metadata. A dedicated Athena
workgroup~\cite{aws-athena-workgroups} manages the query execution, saving the
result datasets to a secondary S3 query results bucket.

During execution, the Lambda function continually polls the query execution
status~\cite{aws-athena-query-execution-status}. Once the query yields a
terminal state, the Lambda handler retrieves the generated results from the
S3 bucket, formats them into a JSON response, and returns them to the API
Gateway. Although Athena queries induce higher latency compared to the live
route, processing is typically completed well within the 29-second timeout limit,
mostly in under 5 seconds.

\subsection{API Gateway and Access Control}\label{sec:api_gateway_access_control}

Amazon API Gateway exposes the live and history routes as managed REST
endpoints and acts as the public entry point for frontend and client
applications~\cite{aws-api-gateway}. Both productive endpoints,
\texttt{POST /live} and \texttt{POST /history}, are integrated with dedicated
Lambda handlers and return structured JSON responses.

To prevent unrestricted public access, both API methods require an API key in
the \texttt{x-api-key} HTTP header. API Gateway validates the key before a
request is forwarded to the corresponding Lambda function. Invalid or missing
keys are rejected at the gateway layer, which avoids unnecessary backend
invocations and separates access-control errors from application-level errors.

The API key is connected to the deployed API stage through an API Gateway usage
plan. This usage plan also allows request throttling and provides a lightweight
access-control mechanism for the current system. The key value is stored in AWS
Secrets Manager instead of being hard-coded in the repository, which separates
credential handling from infrastructure code and supports later key rotation.

Since the API is consumed by a web frontend, Cross-Origin Resource Sharing
(CORS) is configured accordingly. In particular, the \texttt{x-api-key} header
and the \texttt{POST} and \texttt{OPTIONS} methods are allowed so that
authenticated browser requests can pass the required preflight checks.

\subsection{SNS-Based Alerting}\label{sec:sns_notifications}

The alerting component notifies users by email when incoming sensor readings
indicate a critical environmental condition. Alert detection is implemented in
the validation Lambda function, which evaluates the transformed sensor payload
before the latest measurement is written to DynamoDB. If one or more critical
conditions are detected, the function publishes an aggregated notification
through Amazon SNS~\cite{aws-sns}.

The current implementation detects flame exposure, excessive temperature, and
high humidity. A flame alert is triggered when \texttt{flame\_digital} is set to
\texttt{true}. Temperature alerts are generated when either the DHT temperature
or the thermistor temperature exceeds \SI{30}{\celsius}. Humidity alerts are
generated when the DHT humidity exceeds \SI{80}{\percent}. The
\texttt{is\_outlier} field is not used for user-facing alerts because it is
reserved for later machine-learning workflows.

To avoid repeated email notifications while the same critical condition remains
active, the system implements a cooldown mechanism. A DynamoDB table stores the
timestamp of the last sent email for each combination of \texttt{device\_id} and
alert reason. Before publishing a new SNS message, the Lambda function checks
this table and only sends a new email if no previous entry exists or if the last
notification is older than five minutes:

\begin{equation}
    t_{\text{current}} - t_{\text{last\_sent}} \geq 300
\end{equation}

This design prevents notification spam while still allowing different alert
types to be reported independently. For example, a temperature alert can be in
cooldown while a newly detected flame alert for the same device is sent
immediately. All active alert reasons that are not currently in cooldown are
combined into a single email containing the affected device, location,
measurement timestamp, original sensor payload, and detected alert reasons.

The validation Lambda is granted only the permissions required to publish to the
SNS topic and to read and update the DynamoDB cooldown table. The implementation
was verified through manual AWS integration tests and automated unit tests with
mocked SNS and DynamoDB interactions, covering alert detection, cooldown
blocking, cooldown expiration, timestamp updates, and conditional SNS
publishing.
